\subsection{The Use Cases}
\label{sec:usecases}

\begin{figure}[h!]
    \centering
    \includegraphics[width=0.5\textwidth]{figs/Final_Use_cases.png}
    \caption{Use cases}
    \label{figs:usecases}
\end{figure}

The system has two types of users: admin users and regular users. 
Admin users are predefined at start-up, with default credentials, allowing immediate login. 
Regular users must create an account before they can log in. 
Both user types can vote on polls, while only admin users can create new polls. 
This design implements role-based authorization, ensuring appropriate access control and tying votes to verified accounts for fairness and security.

\subsection{The Domain Model}
\label{sec:design}

\begin{figure}[h!]
    \centering
    \includegraphics[width=0.6\textwidth]{figs/Final_domain_model.png}
    \caption{Domain Model}
    \label{figs:logo}
\end{figure}

The domain model consists of several key entities that manage users, polls, votes, and vote options. 

Each poll must have exactly two options. This restriction ensures that the poll remains meaningful, as a poll with only a single option would not make sense. Admin users are not permitted to add additional options beyond these two.

Each user is allowed to vote for only one option per poll. This restriction is in place to prevent multiple votes from a single user, ensuring that the results remain accurate and fair. However, one could argue that in cases where a question has multiple valid answers, users should be able to select more than one option. Examples of such questions include “When would you like to have this week’s meeting?” or “Which ice cream flavors do you like the most?” For simplicity, this functionality is not supported.

Each user can vote only once per poll. It is unnecessary for a single user to cast multiple votes for the same poll option, so the system ensures that only one vote per user is allowed.

The following sections describe each entity in detail.

\subsubsection{User entity}


The User entity represents an application user and stores profile information and the polls the user has created. It is a persistent JPA entity and serves as the aggregate root for the user aggregate.


The user domain consists of:

\begin{itemize}
    \item \textbf{id:} Primary key, unique identifier for each user (auto-generated, Long).
    \item \textbf{userId:} Public identifier suitable for links or external references (String).
    \item \textbf{username:} Display name of the user (String).
    \item \textbf{password:} User's password for login and authentication (String).
    \item \textbf{email:} Contact email (String).
    \item \textbf{roles:} Set of roles assigned to the user (Set\<Role\>). Default role is $NORMAL$, alternative is $ADMIN$.
    \item \textbf{created:} Set of Poll entities created by the user (Set\<Poll\>). One-to-many relationship with CascadeType.ALL and orphanRemoval = true.
    \item \textbf{Domain methods:} 
        \begin{itemize}
            \item \texttt{createPoll(String):} Creates a new poll associated with this user and adds it to the \texttt{created} set.
            \item \texttt{voteFor(VoteOption):} Creates a new vote for the specified vote option and associates it with this user.
        \end{itemize}
\end{itemize}

\subsubsection{Poll entity}

The Poll entity represents a poll in the application, consisting of a question and a list of possible answers (VoteOption entities). Users select one of these options when casting a vote. Poll acts as the aggregate root for its VoteOption entities.


The poll domain consists of:

\begin{itemize}
    \item \textbf{id:} Primary key, unique identifier for each poll (auto-generated, Long).
    \item \textbf{pollId:} Public identifier suitable for links or references (String).
    \item \textbf{question:} The question or statement that users are voting on (String).
    \item \textbf{options:} List of VoteOption entities representing the possible answers (one-to-many relationship).
    \item \textbf{publishedAt:} Timestamp indicating when the poll was published.
    \item \textbf{validUntil:} Timestamp indicating when the poll is no longer valid (e.g., voting closes).
    \item \textbf{createdBy:} Name or username of the person who created the poll (plain text).
    \item \textbf{createdByUser:} Reference to the User entity who created the poll (@ManyToOne relationship).
    \item \textbf{Domain methods:}
        \begin{itemize}
            \item \texttt{addVoteOption(String):} Adds a new option to the poll with the given caption, sets its presentation order, and returns the created \texttt{VoteOption} object.
        \end{itemize}
\end{itemize}

\subsubsection{VoteOption entity}

The VoteOption entity represents a single possible answer or choice within a poll. Each poll contains a list of VoteOption entities, and users select one of these options when casting their vote. VoteOption is associated with a specific Poll. This entity is part of the poll aggregate. While VoteOption could have been modeled as a value object, we chose to implement it as an entity because it has its own unique identifier and can be independently referenced, for example to track votes for each option.


The voteOption domain consists of:

\begin{itemize}
    \item \textbf{id:} Primary key, unique identifier for each vote option (auto-generated, Long).
    \item \textbf{caption:} Text or label describing the option (String).
    \item \textbf{presentationOrder:} Order in which the option is presented in the poll (int).
    \item \textbf{votes:} Number of votes received (int).
    \item \textbf{poll:} Reference to the Poll entity this option belongs to (Many-to-one relationship).

\end{itemize}

\subsubsection{Vote entity}

The Vote entity represents a single vote cast by a user for a specific option in a poll. Each vote records which user voted, for which poll, and which option was selected. Vote acts as an entity in the domain model and is associated with a VoteOption. This entity is part of the poll aggregate.
The vote domain consists of:

\begin{itemize}
    \item \textbf{id:} Primary key, unique identifier for each vote (auto-generated, Long).
    \item \textbf{userId:} Identifier of the user who cast the vote (String).
    \item \textbf{pollId:} Identifier of the poll in which the vote was cast (String).
    \item \textbf{optionIndex:} Index of the option selected by the user (int).
    \item \textbf{publishedAt:} Timestamp indicating when the vote was cast (Instant).
    \item \textbf{votesOn:} Reference to the VoteOption entity this vote is associated with (Many-to-one relationship).

\end{itemize}


\subsection{The Component architecture}


Here is the component architecture for our project:

\begin{figure}[h!]
    \centering
    \includegraphics[width=0.5\textwidth]{figs/arkitektur_figur.drawio (1) (1).png}
    \caption{Our architecture}
    \label{figs:logo}
\end{figure}

Our software architecture consists of a React frontend built with Vite for a fast and interactive user interface. 
The REST API, implemented with Spring Web MVC, serves as a bridge between the frontend and the core business logic, 
which is handled by Spring components and services. 
Data persistence is managed using the Jakarta Persistence API with Hibernate, storing application data in an H2 database. 
For messaging, we use RabbitMQ. 
Additionally, we use Neo4j instead of Redis for caching, which will be explained further in the technology section.
